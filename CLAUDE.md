# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TechDigest is a batch pipeline that collects news from RSS feeds (technology + Brazilian politics), has an LLM write a summary and a multi-voice podcast script for each item, synthesizes the audio with Edge-TTS, and delivers each item to Telegram. It is meant to run unattended from a systemd timer (the unit files are not in this repo).

Everything in the codebase is written in Brazilian Portuguese: identifiers, comments, docstrings, log messages, LLM prompts and commit messages. Keep new code consistent with that.

## Commands

```bash
.venv/bin/pip install -e .                       # install (already installed editable in .venv, Python 3.14; requires >=3.11)
.venv/bin/techdigest                             # run the pipeline (same as: .venv/bin/python -m techdigest)
.venv/bin/python scripts/resumo_lotes.py         # per-run summary table parsed from today's log
.venv/bin/python scripts/resumo_lotes.py 07/10   # same, for a given day (DD/MM)
.venv/bin/python scripts/testar_agrupamento.py   # grouping diagnostic: no Telegram, digest.db opened read-only, LLM only with --etapa3
.venv/bin/python scripts/testar_episodio.py --amostra <file>   # generates a few episodes from a saved sample: LLM only, nothing delivered
.venv/bin/python scripts/checar_fidelidade.py    # checks those episodes against the source texts of their pautas: no LLM, no network
.venv/bin/pip install -e '.[dev]'                # dev extra (pytest)
.venv/bin/pytest                                 # tests
```

- `scripts/testar_agrupamento.py` collects the feeds, extracts the texts (about a minute of network I/O), prints the "pautas" it would form and writes the top-scoring pairs to `data/agrupamento/pares_<timestamp>.csv`. Options: `--limiar`, `--peso-titulo`, `--max-candidatos`, `--incluir-vistos`. Every live collection returns different articles, so to compare thresholds on the same data use `--salvar-amostra` (also writes the extracted candidates to `data/agrupamento/amostra_<timestamp>.json`) and then `--amostra <file>`, which reruns the comparison on a saved sample with no network access. On a saved sample, `--rotulos <csv>` checks the result against hand-labelled pairs, and `--etapa3` asks the project's LLM to confirm each provisional pauta (one call per pauta, repeated with `--repeticoes N`) and writes `data/agrupamento/etapa3_<timestamp>.csv`. Before using `--etapa3`, make sure the LLM server is up and that no pipeline run is in progress or about to start, since both would compete for the model.
- `scripts/testar_episodio.py` rebuilds the final pautas of a saved sample (stages 1 to 3) and calls `Summarizer.process` for up to 4 multi-source pautas plus one single-source pauta as a control. `--repetir <relatorio>` reuses the pautas of an earlier report instead (same articles, order and relations, no stage 3), `--pautas "86+71;12"` adds pautas built from sample ids (the longest text is the principal), `--so-lados` runs only the side analysis of each pauta, and `--pasta <name>` picks the output folder under `data/agrupamento/` (default `episodios`). It writes each episode and a `relatorio_<timestamp>.json` (or `lados_<timestamp>.json`), rewritten after every pauta, prints memory, swap and temperatures before every LLM call, plus the memory of its own process and of the Ollama processes (resident, anonymous and swapped) and the RAM held by the compressed swap (zram), records which correction each episode needed and how much of each source went into it, the answer and excerpt of each actor, the thin sides and the minimum applied to each analyst, the roles, the number of turns and the analysts' sentences in the first person plural (a diagnostic only), and stops if available memory drops below `--min-memoria` GiB or if Ollama stops answering or unloads the model mid-run. The swap is only recorded: on this machine it fills up during generation with plenty of memory available. On the local model a generation call takes about 2 minutes. The script's own output goes to stdout only: redirect it to a file under `data/`, not `/tmp`. Same precautions as `--etapa3`.
- `scripts/checar_fidelidade.py` reads a `relatorio_<timestamp>.json` written by `testar_episodio.py` (the latest one by default, or `--relatorio <file>`), loads each episode and the articles of its pauta from the sample, and writes `data/agrupamento/fidelidade_<timestamp>.txt`. It lists the numbers, percentages and proper nouns of the title, `resumo_didatico`, `pontos_chave` and turns that appear in no text of the pauta (a number written out counts as its numeral), vague attributions ("especialistas afirmam") to a group the pauta never cites (the detection lives in `ai/atribuicoes.py` and the reading of numbers in `ai/numeros.py`, both also used by the QA), outlets missing from `fontes_citadas`, and, when `houve_divergencia` is true, fewer than two analysts and turns where Helena seems to take a side. It compares text, not meaning: a correct number used to say something else passes, and the Helena check is a word list. The equivalences and blind spots are in `COMO_LER`, printed at the top of every report. It is a diagnostic only: the pipeline does not use it, and of its checks only two are also QA rules: the attribution to a group the pauta never cites, and percentages and numbers from 10 up that no text of the pauta carries. Smaller numbers and proper nouns stay in the diagnostic only.
- Tests cover the pure functions in `processing/agrupamento.py`, the JSON parsing and the options each call sends in `ai/llm.py`, the input budget, the `process` flow and the four kinds of correction in `ai/summarizer.py`, the validation of the side analysis, the answers per actor with their excerpts, the thin sides, the caveats, the new attempt and the block in `ai/lados.py`, the source, title, analyst, role, caveat, attribution and number rules in `ai/qa.py`, with the field each problem belongs to, the reading of numbers in `ai/numeros.py`, together with the position verbs of `ai/verbos.py` (all through fake clients; no test calls an LLM), and the rules of `scripts/checar_fidelidade.py` (pytest finds the scripts through `pythonpath = ["scripts"]` in `pyproject.toml`). There is no linter and no formatter configured. `requirements.txt` is empty and gitignored; dependencies live in `pyproject.toml`.
- **Running the pipeline has real side effects and there is no dry-run mode**: it calls the LLM, sends messages and audio to the configured Telegram chat, and marks URLs as seen in `data/digest.db`. Do not run it just to check a change; exercise the individual function instead (e.g. `collect_rss()`, `extract_full_text(url)`, `qa.problemas(result, veiculos, lados, ressalvas, textos)`).
- Always enter through `techdigest.main` (the console script or `python -m techdigest`). `python -m techdigest.pipeline` skips `setup_logging()`, so nothing reaches the log file.
- System requirements outside pip: `ffmpeg`/`ffprobe` on PATH (audio concat and duration), network access for Edge-TTS, and an Ollama server at `OLLAMA_HOST` when `LLM_PROVIDER=ollama`.

## Configuration

- All settings are fields of `Settings` in `src/techdigest/config.py` (pydantic-settings), read from `.env` at the repo root. The env var name is the field name in upper case (`max_news` → `MAX_NEWS`).
- Reading `.env` is denied in `.claude/settings.json`. Use `config.py` as the reference for which keys exist and their defaults, and ask the user for actual values. The feed list in particular comes from `RSS_FEEDS` (comma-separated) in `.env`; the defaults in code are not what runs in practice.
- Every module creates its own `settings = Settings()` at import time, and `ai/qa.py` copies the `QA_*` limits into module constants at import. Settings therefore cannot be overridden in one place at runtime; an override has to be in the environment before the modules are imported.
- `LLM_PROVIDER=ollama` selects `OllamaProvider`; any other value selects `OpenAIProvider`, which covers every OpenAI-compatible endpoint (Groq, OpenRouter) through `OPENAI_BASE_URL`.

## Editorial rules

The rules below are the ones in force today. They are referred to by name, not by number: the comments in the code mention "regra 1", "regras 2, 3 e 6" and similar, but the numbered list is not in the repository and those numbers could not be matched to specific rules. Do not infer a number's meaning from the code; ask the owner.

**Verified by code.** An item that violates one of these gets one correction (see "The corrections" below) and, if it still violates, is skipped (`ai/qa.py`):
- Summary with 7 to 10 sentences (`resumo_didatico`). The prompts ask for 8 to 9, plus one closing sentence about the debate when `houve_divergencia` is true, to leave a margin.
- Script with 240 to 480 words per character. The analyst of a thin side (see "The side analysis") has a lower minimum, `QA_MIN_LADO_FINO` (120); the totals do not change.
- Script with 600 to 1300 words in total.
- Every speaking character is declared in the cast, and every declared character speaks.
- Source text with at least 1200 characters, so headlines alone never become an episode (`pipeline.py`).
- Article published no more than 7 days ago (`MAX_IDADE_DIAS`).
- When an episode has two or more outlets as sources, every one of them appears in `fontes_citadas` (accent- and case-insensitive, one name may be contained in the other, compared by whole words). Single-source episodes are not affected, and the pipeline only produces single-source episodes today.
- Title without percentages or proportions (`proporcoes_no_titulo`): no percentages, no "x vezes" (nor "dobro", "triplo", "quádruplo") and no proportions ("metade", "um terço", "três em cada quatro", "6 de 11", "a cada 9 horas", "maioria", "minoria", "maior parte", "grande parte"). An absolute quantity passes, in digits or written out, with or without "quase", "mais de" and similar ("12 mortos", "doze mortos", "mais de 100 mortos"), and so do years, ordinals and names that carry a digit ("Eleições 2026", "1º turno", "escala 6x1").
- Analysts per side (`problemas_dos_analistas`), for every episode. The side analysis (see "The side analysis" below) says how many sides the pauta has, from 1 to 3. The episode must have exactly one analyst per side (Helena does not count), and `houve_divergencia` must be true if and only if there are two sides or more. With two sides or more there must be a one-to-one match between analysts and sides in which each analyst has one sentence that cites an outlet of that side, uses a position verb and names an actor that only that side has. An actor counts as named when the sentence has more than half of the words of its name that no actor of another side uses, so "Nunes Marques" stands for "Kassio Nunes Marques", while a name of one or two words must appear in full. The position verbs are a closed list of inflected forms in `ai/verbos.py` (16 verbs, third person present, preterite and imperfect, singular and plural, plus the gerund), compared as whole words and accent-sensitive, so "negócio" is not "nega" and "crítica" is not "critica".
- Caveats (`problemas_das_ressalvas`). Each caveat of the pauta must appear in a turn of Helena that contains a question mark and has one sentence that cites an outlet of the caveat, names one of its groups and uses a position verb ("Segundo a Gazeta do Povo, economistas alertam que... Como você vê isso?"). The group counts by its main word (the first one that is not an article, a particle or a quantifier), in any number or gender, so "pesquisadora" stands for "pesquisadores"; a form of a position verb is not a group term ("critica" is not "críticos"). A caveat with no group only needs the outlet, the verb and the question mark. The rule checks the form, not whether Helena evaluates the caveat.
- No attribution to a group that the pauta never cites (`problemas_das_atribuicoes`). The title, the summary, the key points and the turns may not attribute anything to an unnamed group ("para os analistas, ...", "especialistas afirmam", "segundo as análises") unless some text of the pauta (title or full text of any of its articles) has a word of the same family. The groups, the attribution markers and the verbs are closed lists in `ai/atribuicoes.py`; "para os <grupo>" only counts at the start of a clause and followed by a comma, and a group preceded by "nossos", "dois" and similar is the cast of the episode, not a source.
- Numbers come from the pauta (`problemas_dos_numeros`). Every percentage, and every other number from 10 up, in digits or written out, in the title, the summary, the key points and the turns must be in some text of the pauta (title or full text of any of its articles). A percentage only matches a percentage, and a decimal said with "vírgula" is read as one number ("cinquenta e oito vírgula oito por cento" is 58,8%). Rounding follows `numeros.tem_fonte`: with "cerca de" or "aproximadamente" the number may be up to 5% away from one of the source; with "quase" the source must be below what is said and with "mais de" above it, also within 5%; with no qualifier only the integer that rounds or truncates a decimal of the source passes (30,7 may be said as 30 or 31). Smaller numbers stay in the diagnostic.
- The role of an analyst (`problemas_dos_papeis`). The field `papel` of a character other than Helena may not carry the name of an actor of the sides ("analista da Meta").

**Requested in the prompt only.** The model is instructed to follow these, but nothing checks them (`ai/prompt.py`):
- Use only information from the sources; do not invent data or quotes.
- Short, attention-grabbing title without sensationalism, derived from `resumo_didatico`: it states nothing the summary does not (only the absence of percentages and proportions is checked by code). The title names the actors as the sources name them, without turning a person into the institution or the state.
- 2 to 5 self-contained key points.
- "Why it matters" section with 1 to 3 sentences.
- Helena is fixed as the presenter and only moderates: she asks, sums up and hands over, without taking a position.
- Script with 10 to 20 turns and 50 to 90 words per turn.
- Helena opens, moderates and closes the episode.
- Written to be spoken: no markdown, URLs or lists.
- Cite outlets by name.
- The question of the block is an internal guide: Helena presents it once, at the opening, in natural words, without repeating it literally and without turning the positions of the sides into questions attributed to the actors. The analysts present the positions.
- With two sides or more, each analyst answers for one side and sustains its position with the arguments of the sources: no criticism of the own position, no endorsement of the other side, no judgement of his own. He speaks in the third person ("a campanha sustenta..."), never as a spokesperson ("nós", "não podemos aceitar"), and the analyst of a thin side does not expand beyond what the sources carry. With a single side the analyst explains the position and answers the caveats with what the sources say, without advocating.
- In `personagens`, `nome` carries only the name and the role goes in `papel`, which states a speciality and no tie to an actor (the tie is checked by code).
- Helena brings each caveat as an attributed question without evaluating it, followed by an open question that does not rephrase the alert in her own words (only the form is checked by code). The code checks the form of the attribution (outlet, position verb and actor in one sentence), not whether it is faithful to the texts, nor Helena's neutrality.
- The episode neither invents a side, actor or position that the sources do not carry nor omits a side or a caveat of the block.
- With several sources, `resumo_didatico` carries the consensus. The sentence announcing the debate only appears, as an extra closing sentence, when `houve_divergencia` is true.

**Other editorial principles in the code:**
- "Boletim duplo": feeds are interleaved so `MAX_NEWS` is not consumed by the first feeds alone, since TechDigest and PulsoBR share each batch (`collectors/rss.py`).

## Architecture

`main.main()` sets up logging and calls `pipeline.run()`, which takes an exclusive `flock` on `data/techdigest.lock` (one run at a time) and then loops over the articles in `pipeline._executar()`:

1. `collectors/rss.collect_rss()` downloads each feed, filters by age (`MAX_IDADE_DIAS`) before applying `MAX_POR_FEED`, and **interleaves** the feeds so `MAX_NEWS` is not consumed by the first feeds only.
2. `storage/dedup.SeenStore` (SQLite table `seen`, keyed by SHA-256 of the URL) skips items already delivered.
3. `processing/extractor.extract_full_text()` fetches the article body with trafilatura. Google News links are first resolved to the publisher URL with `googlenewsdecoder`; trafilatura is never run against a google.com URL (it would return the cookie-consent page). Items with less than `MIN_TEXTO_CHARS` of text are discarded.
4. `ai/summarizer.Summarizer.process()` cuts the texts to a size budget (see below), asks the LLM for the question in dispute and the sides of the pauta (`ai/lados.py`, one short call with `PROMPT_LADOS`, repeated once if the answer is not valid), calls the provider with `PROMPT_SISTEMA` and the input that now carries the sides, runs the deterministic checks in `ai/qa.py`, and on failure makes **one** correction call, of the kind the problems ask for (see "The corrections" below). If the corrected episode still fails it raises `QAReprovado`. Every item therefore costs two LLM calls, plus one when the side analysis has to be retried and one more with a correction.
5. `audio/tts.gerar_podcast()` synthesizes one mp3 per dialogue turn, inserts silences with ffmpeg and concatenates into `data/audio/<slug>.mp3`.
6. `delivery.deliver_item()` sends the text and then the audio to Telegram, and only after that does the pipeline call `seen.mark_seen()`.

Invariants worth preserving:

- **Deliver first, mark seen after.** An interrupted run neither loses nor repeats a delivered item, and anything not delivered comes back on the next run. This includes QA rejections (retried next run) and the case where the text was sent but the audio upload failed (`AudioNaoEnviado`): the item is not marked seen, so the next run sends it again in full.
- **One bad item never kills the run.** Generation errors are caught per item and logged. Only `MAX_FALHAS_ENTREGA` consecutive delivery failures abort the run, by raising, which makes `main` exit with status 1 for systemd.
- **Time budget.** No new item starts after `MAX_RUNTIME_MIN`; the systemd unit kills the process at 4 hours.
- **The Telegram token must not reach the logs.** The token is part of the request URL and `requests` errors quote the URL, so `delivery/telegram._post` re-raises with `from None` and without the URL.

### The input budget

`summarizer.montar_entrada()` builds the message for the episode and keeps it inside a character limit, so the provider never has to truncate it:

- Headers, the editor's notice (`AVISO DO EDITOR-CHEFE`), the block of sides (`LADOS DA PAUTA`) and the reminder are never cut. `MAX_BLOCO` characters are always set aside for the block, whatever its real size, so the texts are cut the same way before the side analysis (which reads them) and in the generation call. The texts share what is left: each keeps its usual ceiling (5000 characters for the principal, 3000 for each of up to 2 related articles); if they do not fit, the principal gets about half and the related ones split the rest, unused share is passed on, and cuts fall at a paragraph end. A related article that would get less than 400 characters is dropped, and the notice only counts and names what was actually included.
- The limit comes from `Summarizer._limite_da_entrada()`. With Ollama it is `OLLAMA_NUM_CTX` minus the output reserve and a margin, converted to characters, minus the system prompt. The reserve is the smaller of `OLLAMA_NUM_PREDICT` and `LLM_RESERVA_SAIDA`, because `num_predict` may be larger than the window itself. With an OpenAI-compatible provider the limit is `LLM_MAX_PROMPT_CHARS`; if a message still exceeds it, `OpenAIProvider` cuts it and logs an error.
- Characters per token start at a conservative 3.0 and are then measured from `provider.ultimo_uso` after every call (90% of the lowest value seen).
- The full revision carries the original episode too, so its source text is rebuilt with what is left of the window and can be much shorter than in the generation call. The revision of the script carries only the script, so it leaves more room for the sources. Both carry the same block of sides. The correction of the summary reuses the excerpts of the generation call, unchanged.
- The limit of an episode is computed once, before the side analysis, and reused for the generation input, even though the side call updates the measured characters per token.

### The side analysis

The analysis asks the LLM for the question in dispute within the story ("questão": a single question that the actors answer in opposite ways, such as "O canal deve ser suspenso?") and for the sides. A side ("lado") is one answer to that question, held by named actors: accusation against defence, decision against criticism, statement against denial. Every actor who gives the same answer is on the same side, even with different arguments, never one side per actor, and a third side only exists when its answer opposes the other two. Complementary information, different details or the mere sequence of events do not make a dispute, and in doubt the story has no question and one side. `Summarizer.preparar()` runs the analysis for every pauta, single-outlet ones included, at temperature 0.1, on the same cut texts that go to generation, each with its outlet and title. The answer is a JSON object whose only required key is `lados`; the question comes first so the model states the dispute, then the answer of each named actor with a literal excerpt that proves it, and only then the sides:

```json
{"questao": "one question, or empty", "respostas_por_ator": [{"ator": "Meta", "resposta": "Não", "trecho": "literal excerpt", "veiculo": "Agência Brasil"}], "lados": [{"resposta": "Não", "posicao": "one sentence", "atores": ["Meta"], "grupos": [], "veiculos": ["Agência Brasil"]}], "motivo": "one sentence"}
```

Only a position with a named actor counts as a side. `atores` are names or specific designations ("Meta", "campanha de Lula", "governo federal"), in the form the texts use most ("Lula", not the full name). `grupos` are unnamed collectives ("economistas", "especialistas") and vague designations with no qualifier ("o governo", "a empresa"). A position held only by groups is a caveat ("ressalva"): it does not count as a side, gets no analyst, and enters the episode as an attributed question asked by Helena.

`lados.analise_da_resposta()` is the pure function that turns the answer into the sides and caveats in force. Each side of the answer needs a position and at least one outlet of the pauta (tolerant comparison, `qa.mesmo_veiculo`). A generic actor, one whose words are all in `lados.TERMOS_GENERICOS`, is moved from `atores` to `grupos` in code, so "governo federal" and "governo do Amazonas" stay actors, and so does a collective with a qualifier ("especialistas em segurança"), which the list does not catch. A side left with no named actor (only groups, or nothing) becomes a `Ressalva` (`grupos`, `posicao`, `veiculos`); in a side that has a named actor the groups are dropped, since they agree with it. At most `MAX_RESSALVAS` (2) caveats are kept, the first ones, with a warning in the log. The named sides must be at most 3, each with an actor that no other side has. The question only stays with two named sides or more, each with its own `resposta`, different from the others (compared without case, accents or punctuation); with one named side the question is dropped, and two or more named sides without a question are invalid. With no named side at all the pauta gets the neutral side (`lado_unico()`: every outlet, no actors, position "relato dos fatos, sem lados definidos") and keeps its caveats. Every outlet of the pauta must be in some side or caveat. One outlet may report more than one side. Actors are compared without accents, case, articles or particles (da, de, do, das, dos, e), and a name contained in another is the same actor ("Lula" and "campanha de Lula"), so it does not separate two sides. `Analise.ajustes` lists what the code changed in the answer.

With a question, the answer must also carry `respostas_por_ator`: for each named actor, its answer to the question and an excerpt copied literally from the text of an outlet of the pauta. `_conferir_atores()` keeps in each side only the actors whose proven answer is the side's: the excerpt must have at least `MIN_TRECHO` characters and be in the title or text that the analysis received from that outlet, that is, the excerpt already cut by the budget (spaces, quotation marks and case are normalised, and quotes or ellipses around it are ignored). An actor with no entry or no proven excerpt is dropped; an actor placed in a side whose answer differs from its own moves to the side with its answer, if there is one, or is dropped; two answers are the same when one starts with the other ("Sim" and "Sim, é desinformação"). A side left with no actor follows the rules above (it becomes a caveat). A question with no `respostas_por_ator` is an invalid answer. Without a question nothing is checked and the actors stay as they came. `Analise.respostas` keeps every entry with the result of the check, and `Lado.trechos` the excerpts of the actors that stayed.

A side with a single evidence excerpt is a thin side ("lado fino", `Lado.fino`; only in pautas with two sides or more, `lados_finos()`): the sources carry little material for it, so its analyst has a lower minimum of words (`QA_MIN_LADO_FINO`) and the block tells him not to expand beyond what the sources carry.

An invalid answer or a failed call gets one new attempt (`lados.analisar_lados()`): the same input plus `pedido_de_correcao()`, which carries the validation error, the refused answer and a reminder to group the actors by their answer to the question. `Analise.primeira` keeps the refused attempt. If the second attempt is not valid either, the pauta goes on with the neutral side and no caveats, with a warning in the log, and the episode has one analyst.

The result reaches the generation as the block `LADOS DA PAUTA` (`lados.bloco_dos_lados()`): the question, the sides with their answers, the caveats right after them, the exact cast (Helena plus one analyst per side; Helena presents the question once, at the opening, and each analyst sustains the position of one side; with a single side the analyst explains and does not advocate), how Helena brings each caveat, which sides are thin and the range of words of their analysts, the value of `houve_divergencia` and the word target per character for that cast size, since four characters at the usual target would exceed the total of 1300 words. The block never exceeds `MAX_BLOCO` characters (1600): the position sentences shrink first, which happens with three sides and two caveats. The model no longer decides whether there is a divergence. The pieces that change together are `PROMPT_LADOS`, `CHAVES_LADOS`, `entrada_dos_lados()`, `analise_da_resposta()`, `_conferir_atores()`, `TERMOS_GENERICOS`, `pedido_de_correcao()`, `bloco_dos_lados()`, the prose about the question, the sides and the caveats in `PROMPT_SISTEMA` and `PROMPT_REVISOR`, and `qa.problemas_dos_analistas()` and `qa.problemas_das_ressalvas()`. The list of position verbs lives in `ai/verbos.py` only: the prompts show the infinitives and the QA accepts the inflected forms.

### The corrections

Every problem found by `qa.problemas_com_campo()` is a `Problema` with the field of the episode it belongs to, and `summarizer.tipo_de_correcao()` picks the single correction the episode gets from those fields:

- **Title** (`"titulo"`): every problem is in the title. A short call with `PROMPT_TITULO` rewrites only the title from the summary. It receives the summary, the actors of the sides, the problems and the original title, no source text, and answers `{"titulo_reescrito": "..."}`.
- **Summary** (`"resumo"`): every problem is in `resumo_didatico`. A short call with `PROMPT_RESUMO` rewrites only the summary. It receives the same excerpts that went to generation (`Entrada.artigos`), whether there is a divergence, the problems and the original summary, and answers `{"resumo_didatico": "..."}`.
- **Script** (`"roteiro"`): every problem is in `roteiro_podcast` (words per character or in total, the match between analysts and sides, caveats, attributions and numbers inside a turn) or in the role of a character. A call with `PROMPT_ROTEIRO` receives the sources, the block of sides, the characters, the problems and the original script, and answers `{"personagens": [...], "roteiro_podcast": [...]}`. From the characters it returns, the code only takes the role of each name that already existed (`_com_os_papeis`): names and order never change.
- **Full revision** (`"completa"`): problems in more than one field, or in a field with no correction of its own (number of analysts, `houve_divergencia`, `fontes_citadas`, key points, malformed JSON). `PROMPT_REVISOR` receives the sources, the problems and the whole episode, and answers the whole episode.

The answer of a targeted correction is merged into the first version, and the QA runs again on the result. `Summarizer.ultimo_diagnostico` keeps the first version, the kind of correction (`correcao`), the input it used (`revisao`) and the last whole episode (`episodio`). The rules about Helena, the analysts and the caveats are written once for the two revisions, in `_REGRAS_DO_ROTEIRO` (`ai/prompt.py`).

### The LLM output contract

The episode is a JSON object with 8 keys (`titulo_reescrito`, `resumo_didatico`, `pontos_chave`, `por_que_importa`, `personagens`, `roteiro_podcast`, `houve_divergencia`, `fontes_citadas`). That shape is repeated in several places that must change together:

- `SCHEMA` / `REQUIRED_KEYS` in `ai/llm.py`. The schema is not sent to the provider (Ollama gets `format="json"`, OpenAI gets `json_object`); only the presence of the required keys is enforced, in `parse_json`.
- The prose in `ai/prompt.py` (`PROMPT_SISTEMA` and `PROMPT_REVISOR`) and the reminder (`LEMBRETE`) appended by `summarizer.montar_entrada`. `PROMPT_TITULO`, `PROMPT_RESUMO` and `PROMPT_ROTEIRO` each ask for one or two of those keys alone, and the revision of the script closes its input with `LEMBRETE_DO_ROTEIRO`.
- The consumers: `ai/qa.py`, `audio/tts.py` and `_render_item` in `delivery/telegram.py`.

There is a second, much smaller contract: the grouping verdict (stage 3 of the news grouping, see "Unfinished or dormant code"). The model receives one provisional pauta, with its articles numbered from 1, and answers with a JSON object whose required keys are `tipos`, `grupos` and `isolados`:

```json
{"tipos": {"1": "fato_unico", "2": "fato_unico", "3": "varios_fatos"}, "grupos": [{"principal": 1, "membros": [{"id": 2, "relacao": "mesmo_acontecimento"}]}], "isolados": [3], "motivo": "one sentence"}
```

`tipos` classifies every article first: `varios_fatos` is a text that covers several unrelated events (agenda, weekly roundup, bulletin, live coverage) and can never be part of a group. `membros` lists the other articles of the group (never the principal), `relacao` is `mesmo_acontecimento` or `desdobramento`, and every number must appear exactly once between `grupos` and `isolados`. A missing or invalid type, id or relation discards the whole verdict and leaves every article on its own. From a valid verdict the code takes who stays together, the types and how the articles relate: an article typed `varios_fatos` is removed from its group even if the model grouped it, and the model's choice of `principal` is ignored. Its pieces must also change together:

- The prose in `PROMPT_AGRUPADOR` (`ai/prompt.py`).
- `CHAVES_AGRUPADOR`, `TIPOS`, `RELACOES`, `entrada_agrupador()` (the text the model receives), `problemas_do_veredito()` and `compor_pautas()` in `processing/agrupamento.py`.

`parse_json(text, chaves)` and `chat_json(system, user, chaves=, temperatura=, max_saida=)` take the required keys and the sampling options per call. With no extra arguments a call is the episode call: `REQUIRED_KEYS` and the values from `.env`. `num_ctx` is never set per call, because changing it makes Ollama reload the model.

The word and turn limits are duplicated too: `ai/qa.py` enforces the `QA_*` settings, while the same numbers (600-1300 total, 240-480 per character, 10-20 turns) are hard-coded in the prompt texts (`PROMPT_SISTEMA`, `_REGRAS_DO_ROTEIRO`) and the two reminders, the 8 to 9 sentences of the summary are in `PROMPT_SISTEMA` and `PROMPT_RESUMO`, and the word targets per cast size are in `lados.ALVO_POR_PERSONAGEM`. Changing `QA_*` in `.env` does not update any of them.

The presenter name `Helena` is fixed by the prompt and mapped to a fixed voice in `tts.VOZ_FIXA`; the other characters get voices in declaration order.

### Logging and the log-summary script

`logging_setup.py` configures the `techdigest` logger once: console at `LOG_LEVEL`, plus `data/logs/techdigest.log` always at DEBUG (rotating, 2 MB x 7). Modules log through `logging.getLogger("techdigest.<module>")`.

`scripts/resumo_lotes.py` parses that file with regexes over the line format and over exact message texts (`=== TechDigest iniciando ===`, `Execução concluída: N notícia`, `Item pulado pelo QA`, `Item descartado`, `Falha ao entregar`, and the Ollama metrics line with `tok/s`, `RAM disp.=`, `CPU=`, `GPU=`). Rewording those messages or changing the format string breaks the script silently. The metrics line is logged once per LLM call, so its averages now include the short side-analysis call of every item.

## Unfinished or dormant code

- **Related articles.** `Summarizer.process(principal, relacionados)`, the prompts, the input budget and the QA source rule support several sources for one story, but `pipeline.py` never passes `relacionados`, so every delivered episode is single-source. The side analysis does run in the pipeline, since it is part of `process`: a single-source item with two sides gets two analysts and `houve_divergencia` true. Multi-source generation is only exercised by `scripts/testar_episodio.py`.
- **News grouping, phases 1 to 3 of 4.** `processing/agrupamento.py` groups articles that tell the same story (the same event, or a direct follow-up of it within the collection window) into "pautas": stages 1 and 2 score every pair by title and text similarity and form provisional pautas of up to `AGRUP_MAX_ARTIGOS` articles (`AGRUP_LIMIAR`, provisionally 0.18, was calibrated on a single labelled sample); in stage 3 the LLM reads the first `AGRUP_CHARS_ETAPA3` characters of each article, confirms each provisional pauta, and `compor_pautas()` builds the final ones. In a final pauta the `principal` is the article with the longest extracted text and every other confirmed article is a `relacionado`, same outlet or not; the relation (`mesmo_acontecimento` or `desdobramento`) only guides the episode. Only `principal` and `relacionados` go to generation. `duplicatas` (republications, detected by text similarity in stages 1 and 2) are not generated but are delivered with the pauta, so `Pauta.links` includes them; `excedentes` (confirmed articles beyond the limit) are neither generated nor delivered, and are meant to come back as candidates in a later run. All of this, plus `extractor.extrair_em_lote()` and the `AGRUP_*` / `EXTRACAO_*` settings, is used only by `scripts/testar_agrupamento.py`: the pipeline does not group yet, and the call to the LLM for stage 3 lives in that script. Phase 3 added the multi-source generation described above (budget, prompts, QA rule). Still to come: the pipeline integration behind `AGRUPAMENTO_ATIVO`, with `mark_seen` per pauta (phase 4).
- **E-mail delivery.** `delivery/email_smtp.py` was never finished (it references a nonexistent `settings.recipients`, and `send_digest_email` does nothing). `delivery/__init__.py` raises `NotImplementedError` for any `DELIVERY_CHANNEL` other than `telegram`.
