# Scripts, tests, simulation and the Ollama unit

> Moved out of `CLAUDE.md` on 04/11/2026, verbatim, so that the context every session and worker loads stays small. `CLAUDE.md` keeps a short summary under the same heading; when this file changes in a way that makes that summary wrong, fix the summary too.

- `scripts/testar_agrupamento.py` collects the feeds, extracts the texts (about a minute of network I/O), prints the "pautas" it would form (provisional ones of up to `AGRUP_MAX_PROVISORIA` articles, and with `--etapa3` final ones of up to `AGRUP_MAX_ARTIGOS` texts, as the pipeline does) and writes the top-scoring pairs to `data/agrupamento/pares_<timestamp>.csv`. Options: `--limiar`, `--peso-titulo`, `--max-candidatos`, `--incluir-vistos`. Every live collection returns different articles, so to compare thresholds on the same data use `--salvar-amostra` (also writes the extracted candidates to `data/agrupamento/amostra_<timestamp>.json`; since phase 4 each candidate also carries `feed`, the URL of the feed it came from, and `categorias`, the RSS categories of its entry, which older samples lack) and then `--amostra <file>`, which reruns the comparison on a saved sample with no network access. On a saved sample, `--rotulos <csv>` checks the result against hand-labelled pairs, and `--etapa3` asks the project's LLM to confirm each provisional pauta (one call per pauta, repeated with `--repeticoes N`) and writes `data/agrupamento/etapa3_<timestamp>.csv`. `--etapa3` runs the GPU checks of `ai/gpu.py` on the log of the Ollama unit (`OLLAMA_LOG`; `--log-ollama <file>` reads another one; see the Ollama bullet below). `--etapa3` takes the model lock (see Architecture in `CLAUDE.md`), so it stops at once, saying who holds it, if a pipeline run, a simulation or another script is using the model, and its calls go through the machine brakes of `ai/maquina.py`, the same as the pipeline's. Start the test session (`systemctl --user start techdigest-teste.target`) before using it.
- `scripts/testar_episodio.py` rebuilds the final pautas of a saved sample (stages 1 to 3) and calls `Summarizer.process` for up to 4 multi-source pautas plus one single-source pauta as a control. `--repetir <relatorio>` reuses the pautas of an earlier report instead (same articles, order and relations, no stage 3), `--pautas "86+71;12"` adds pautas built from sample ids (the longest text is the principal), `--so-lados` runs only the side analysis of each pauta, and `--pasta <name>` picks the output folder under `data/agrupamento/` (default `episodios`). With `LLM_PROVIDER=ollama` it runs the GPU checks of `ai/gpu.py` on the log of the Ollama unit (`OLLAMA_LOG`, or `--log-ollama <file>`): it stops before loading the model if the NVIDIA driver does not answer or if the log shows that the server did not find the GPU, and after the first call it stops and unloads the model if the log shows the main model with no layer on the GPU. It writes each episode and a `relatorio_<timestamp>.json` (or `lados_<timestamp>.json`), rewritten after every pauta, prints memory, swap and temperatures before every LLM call, plus the memory of its own process and of the Ollama processes (resident, anonymous and swapped) and the RAM held by the compressed swap (zram), records which correction each episode needed and how much of each source went into it (which paragraphs entered each call that carries source text and why: lide, excerpt of side N, text order; and the paragraphs with an evidence excerpt that were left out, in the generation and in each revision), the answer and excerpt of each actor with what proves it carries the answer (`prova`) and the actors whose excerpt was refused, with the reason, for pautas with a dispute the analyst turn that repeats most words of each evidence excerpt (a word-overlap measure, not a rule), how many sentences of the texts mention the actors of each side, the thin sides and the word range applied to each analyst, the word budget of the pauta (`orcamento`, with the plan of the turns) and, for each character and the total, its target, range and how many words above the range it went (`alvo_por_personagem`, `alvo_do_total`; a diagnostic only), whether the script followed the plan (turns and average words of each character against the plan, and the order of the turns), who closes the episode (`plano_seguido.termina_com`; the QA does not check it) and, for each analyst, the side, the words, the target and the sentences of the side in the cut (`plano_seguido.analistas`; all diagnostics only), the thin-side analysts above 200 words (a diagnostic only, see the editorial rules in `CLAUDE.md`), the roles, the number of turns and the analysts' sentences in the first person plural (a diagnostic only), and stops if available memory drops below `--min-memoria` GiB or if Ollama stops answering or unloads the model mid-run. With the CPU above `--max-cpu` (95 °C) before a call, it waits until the CPU is below `--retomar-cpu` (85 °C) and goes on; after 15 minutes of waiting it stops. The swap is only recorded: on this machine it fills up during generation with plenty of memory available. On the local model a generation call takes about 2 minutes. The script's own output goes to stdout only: redirect it to a file under `data/`, not `/tmp`. The memory, temperature, Ollama and GPU checks are the machine brakes of `ai/maquina.py` (the script only adds the per-call record), it takes the model lock before anything else, and its own stage 3 goes through the same brakes. Same test session as `--etapa3`.
- `scripts/checar_fidelidade.py` reads a `relatorio_<timestamp>.json` written by `testar_episodio.py` (the latest one by default, or `--relatorio <file>`), loads each episode and the articles of its pauta from the sample, and writes `data/agrupamento/fidelidade_<timestamp>.txt`. It lists the numbers, percentages and proper nouns of the title, `resumo_didatico`, `pontos_chave` and turns that appear in no text of the pauta (a number written out counts as its numeral), vague attributions ("especialistas afirmam") to a group the pauta never cites (the detection lives in `ai/atribuicoes.py` and the reading of numbers in `ai/numeros.py`, both also used by the QA), outlets missing from `fontes_citadas`, and, when `houve_divergencia` is true, fewer than two analysts and turns where Helena seems to take a side. As a diagnostic only, it also lists, when the pauta has two outlets or more, every sentence of the summary and the turns that attributes something to an outlet ("segundo o Jornal do Vale", "de acordo com", "conforme", or the outlet followed by a reporting verb such as "relata"), with the share of its content words found in the full text of the cited outlet and the highest share found in another outlet of the pauta; content words are compared by a root without plural, gender and verb endings, and the names of outlets, actors and characters and the words that every text of the pauta has do not count. A sentence where another outlet has the larger share is marked; the "strict rule" marks the ones with at least 5 counted words and another outlet 40 points or more above the cited one (on the four rounds of 12 to 14/10/2026 it marked 6 sentences, 5 of them wrong attributions checked in the texts; the thresholds were chosen looking at the first three, and it stays a diagnostic). In episodes with a dispute it shows, for each side, the analyst sentence that presents it (by the QA rule), the outlet it cites and that same measure. Open questions to a group (see the attribution rule in the editorial rules of `CLAUDE.md`) are listed apart, outside the count, to show what that exemption lets through, and only this diagnostic, not the QA, also counts "Para os <grupo> <qualificador>, ..." at the start of a sentence as a vague attribution. It compares text, not meaning: a correct number used to say something else passes, and the Helena check is a word list. The equivalences and blind spots are in `COMO_LER`, printed at the top of every report. It is a diagnostic only: the pipeline does not use it, and of its checks only two are also QA rules: the attribution to a group the pauta never cites, and percentages and numbers from 10 up that no text of the pauta carries. Smaller numbers and proper nouns stay in the diagnostic only.
- `scripts/refazer_qa.py <folder or report>...` measures the effect of a change in the QA on the episodes already generated: for each episode of a `testar_episodio.py` report (a folder counts by its latest `relatorio_*.json`) it rebuilds the input of the QA (the outlets that entered the generation, the sides as the analysis left them, with the thin side recorded, the caveats, the full texts of the pauta from the sample, and the word budget: the one the report recorded or, in reports from before it, one recomputed from the words of the paragraphs that entered the generation; without that record, none, and the minimums of before apply), runs `qa.problemas_com_campo` on the recorded episode (for a rejected one, the version that came out of the correction) and compares with the recorded situation. It lists the episodes that change, with the reason, and, for those that become approved, what `checar_fidelidade.py` finds in them that the QA does not catch. It writes `data/agrupamento/refazer_qa_<timestamp>.txt`. Neither tool sees whether the side analysis chose the right question.

- **Simulation** (`techdigest --simular <folder>`, `simulacao.py`): collection, extraction, LLM and TTS are real; the delivery goes to files in `<folder>/entregas` through the `arquivo` channel (`delivery/arquivo.py`: for each item the text exactly as Telegram would receive it, `_render_item` in HTML, the whole episode as JSON and the mp3, plus `entregas.txt` with the order and the end of the batch); the database is a copy, `<folder>/digest.db`, made with `--banco-origem` opened read-only (`mode=ro`) and SQLite's backup; the log, the audio and the record of each run (`<folder>/execucoes`) stay in the folder, away from the log `resumo_lotes.py` reads by default, and the stop notice goes to `<folder>/AVISO.txt` and to stderr. A new folder must not exist or be empty and needs `--banco-origem`; a folder of an earlier simulation (marked by `.simulacao`) goes on with its own database, which is how a second run is simulated; any other folder is refused, so a simulation never writes to a database that is not its own. `simulacao.preparar()` puts the folder's paths, `DELIVERY_CHANNEL=arquivo`, empty `TELEGRAM_TOKEN` and `TELEGRAM_CHAT_ID` and `TECHDIGEST_SIMULACAO` in the environment before anything of the package reads the configuration (the environment beats the `.env` in pydantic-settings), which is why `main.py` imports the package inside `main()` and `simulacao.py` uses only the standard library. No path of the simulation calls the Telegram API: the channel is `arquivo`, the token is empty, and `delivery/telegram._post` refuses to run with `TECHDIGEST_SIMULACAO` set; the `arquivo` channel in turn refuses to run outside a simulation, where it would mark items as seen in the production database without delivering them. `--sem-audio` skips the TTS, for work simulations only; the simulation that clears the merge has audio. With `AGRUPAMENTO_ATIVO=true` in the environment (it beats the `.env`) a simulation runs with the grouping on. Put the folders under `data/simulacoes/`.
- The Ollama server runs as the user unit `deploy/systemd/ollama.service`, not by hand. The owner installs it (copied into `~/.config/systemd/user/`, with `~/.local/state/techdigest/` created beforehand). It has `StopWhenUnneeded=yes`, so it stays up only while an active unit needs it, and a `systemctl --user start ollama.service` by hand stops it right away; for test rounds that unit is `techdigest-teste.target` (`BindsTo=` the server, so the session falls if the server falls). The unit does not start without the NVIDIA driver (`ExecStartPre=nvidia-smi -L`) and only becomes active once the server has logged its `inference compute` line with `library=CUDA`; otherwise it fails and the server is stopped before any model is loaded. So when `systemctl --user start` returns, the server answers and the log already has the device. Its output goes to `OLLAMA_LOG` (default `~/.local/state/techdigest/ollama_serve.log`, the `%S/techdigest` of the user units, outside both project folders): emptied by `ExecStartPre` at each start and written in append mode, because with `truncate:` every command of the unit, `ExecStartPost` included, empties the file again; and systemd opens it before it would create a `StateDirectory=`, which is why the folder comes from the installation. The unit sets `LLAMA_ARG_CACHE_RAM=0`. The variable reaches the `llama-server` process that runs the model and turns off its prompt cache (the log then says "prompt cache is disabled"). The model uses sliding window attention (SWA), so the cache is never reused between calls, and with the default of 8192 MiB the anonymous memory of `llama-server` kept growing during a run (from 1.1 to 2.0 GB in five episodes, and available memory dropped by about 2 GB); with the cache off it stays flat, at the same speed. The GPU checks of the scripts read the same `inference compute` line in that log, and refuse a log of another start of the server, which is what a server started by hand gets. Without the GPU, Ollama loads the whole model into RAM and on this machine the memory runs out during the load; `ai/gpu.py` holds the checks (`conferir_antes_de_carregar`, `modelo_na_gpu`), used by the pipeline and the scripts through the machine brakes (`ai/maquina.py`). After the load, `/api/ps` only confirms that the model is loaded: the size it reports (1.2 GiB, 0.9 of it on the GPU) does not describe this model. The check reads in the log the last load of the main model, the `--model` file of the line `loading model via llama-server`: its `offloaded N/M layers to GPU` (27/31 on this machine, with 2.6 GiB on the GPU and 15.9 GiB mapped in RAM, the MoE weights staying in RAM) and its buffer sizes. The lines after `loading draft model` belong to the draft model, which fits entirely on the GPU (5/5) and would let a main model entirely on the CPU pass. With no layer of the main model on the GPU, or no load in the log, it unloads the model and stops. It also reports the video memory of `llama-server` from `nvidia-smi`, as information.
